### Schema specifics

- `Request` fields include required `userId` (User ref), `dates[]`, `amountEgp`, `paymentStatus`, `status`; optional region/review fields; `tripIds[]` (Trip refs); note; Kashier session/order IDs, transaction IDs and `paidAt`. `paymentStatus` is `pending | paid | failed | refunded | expired`; `status` is `pending_payment | waiting_list | approved | rejected | submitted | matched | confirmed | active | completed | cancelled | time_out` (`Request.ts:L8-L66`). Request has no direct Payment or Promo ref: legacy payment identifiers/state live on Request and the runtime resolver treats its ID as a `bookingId`; promo usage is on child Trips.
- `Trip.requestId` is an optional indexed Request ref (required before `246eefb`); `userId` is a required User ref; `date`, `cycleIndex`, `paymentId` (Payment ref), fare/promo, and required payment/lifecycle status fields live on the Trip (`Trip.ts:L92-L117`, `L206-L230`). Request and Trip use matching `paymentStatus` values; their lifecycle enums differ. Trip added `waiting_list`, `approved`, and `rejected` in `246eefb`; indexes include `{requestId:1,date:1}`, `{userId:1,date:-1}`, `{driverId:1,date:-1}`, a non-unique partial waiting-list status index, and sparse Kashier order index (`Trip.ts:L310-L317`). `tripNumber` is unique+sparse (`Trip.ts:L86-L90`).
- `Payment.bookingId` is required and declares `ref: "Booking"`; it is not a typed Request/Trip reference. No database foreign keys are enforced by Mongoose refs. The unique partial Payment index allows at most one in-flight record per `bookingId` while `overallStatus` is `created | wallet_reserved | kashier_pending`; a unique sparse `idempotencyKey` is separate (`Payment.ts:L31-L40`, `L87`, `L100-L113`). It does **not** enforce one Payment total per Request or Trip.
- `PromoCodeUsage` references one Trip, PromoCode and User. There is no group-level promo relation (`PromoCodeUsage.ts:L5-L7`).

**Database/migration note:** Mongo/Mongoose models and index scripts are present; no conventional versioned schema migration or Request/Trip collection-drop migration was found. `Request` and `Trip.requestId` support remain in source. Actual deployed indexes and whether legacy rows exist were not checked.

## B. Current-state flows

### New one-day booking
1. `POST /api/trips` accepts one date/one trip after `getMultiTripBookingError`; multiple dates/cycles are rejected in the current worktree (`src/lib/tripBooking.ts:L1-L11`; `src/app/api/trips/route.ts:L181-L199`).
2. It validates the date/window, vehicle/route/time and spacing, recomputes fare and reserves promo per Trip; the one-day path inserts a Trip with `requestId` omitted (`route.ts:L201-L206`, `L423-L577`, `L606-L724`, `L795`).
3. Checkout is a later call to `/api/payments/session`; that resolver treats only `requestId == null` as standalone, creates/uses a Payment, and requests Kashier or wallet settlement (`payments/session/route.ts:L369-L384`, `L428-L430`; `resolvePayableBookingRecord.ts:L64-L79`).

### Old multi-day Request creation (historical, parent `ca95928` of `246eefb`)
1. `POST /api/trips` accepted dates and up to 10 configured cycles, deduplicated dates, silently capped at seven, then validated the selected window (`ca95928:src/app/api/trips/route.ts`, POST, `L147-L185`).
2. It expanded dates × cycles into child Trips with required `requestId`, calculated per-Trip prices/promos, summed them to Request `amountEgp`, then created one Request and inserted all Trips in one Mongo transaction (`ca95928:src/app/api/trips/route.ts:L606-L700`).
3. The Request owned aggregate payment/review state; Request and children were synchronized on settlement. The old Request creation branch was removed from `POST /api/trips` by `246eefb`; the model and GET APIs remain. The current `/api/requests` route has no POST.

### Validation and pricing

- Both historical and current routes validate `YYYY-MM-DD` dates within the seven-date booking window. Historical code silently truncated dates to seven, accepted 1–10 cycles, required valid `HH:mm` pickup/arrival times and snapped shared-ride arrival slots to their midpoint (`ca95928:src/app/api/trips/route.ts:L140-L153`, `L476-L485`; current `bookingDates.ts:L9-L20`, `api/trips/route.ts:L522-L545`; `pickupWindow.ts:L22-L23`).
- **The pre-migration Request creation route did not enforce the current 30-minute spacing rule.** `246eefb` added same-date ±15-minute arrival windows and a 30-minute gap. Current checks compare each candidate to the user’s holding-status Trips across booking groups and previous candidates in the same batch (`tripSpacing.ts:L6-L7`, `L59-L93`; `api/trips/route.ts:L752-L795`). The one-date/one-cycle guard makes multi-child comparisons unreachable in the current worktree.
- Historical pricing was computed per Trip/date; promo was also reserved per Trip, so a promo could apply to some but not all children. Those per-Trip prices were summed into the one Request amount (`ca95928:src/app/api/trips/route.ts:L606-L700`; current fare helper `vehicles.ts:L286-L319`; promo `promoCode.ts:L115-L186`).

### Old Request payment and settlement
1. Request checkout resolves the parent Request (or a child Trip back to its Request), uses aggregate Request amount, creates/claims a Payment, reserves wallet funds and/or creates a Kashier session (`payments/session/route.ts:L223-L225`, `L901-L925`).
2. Webhook/callback supports older Kashier orders with no Payment document and newer mixed Request Payments (`payments/webhook/route.ts:L430-L501`, `L566-L700`; `payments/kashier.ts:L79-L100`, `L107-L252`).
3. On successful Request settlement it syncs the Request and child Trip statuses and notifies the passenger (`payments/webhook/route.ts:L479-L501`). The ordering has a capture failure window described in D.

### Expiry
1. Protected `POST /api/trips/expire` (GET aliases POST) handles pending Request expiry and child state, then invokes standalone expiry (`expire/route.ts:L20-L71`, `L96-L97`).
2. Standalone expiry is a separate `requestId == null` path that defers for a recent in-flight Payment, then expires/cancels the Trip and releases wallet/promo reservation (`services/standaloneTripExpiry.ts:L112-L200`, `L301-L360`).
3. Request list/detail reads also invoke expiry (`requests/route.ts:L46-L48`; `requests/[id]/route.ts:L18-L20`). The route notes Vercel Cron, but no schedule declaration is in-repo; actual recurring invocation is external/deployment configuration. The Postman collection documents a manual CRON-secret request (`postman.collection.json:L69-L72`, `L1112-L1127`).

### Cancel/refund
1. Current passenger cancellation is Trip-ID based. For a Request-backed child it checks parent Request payment/review state; for a standalone Trip it uses its own payment state (`trips/[id]/cancel/route.ts:L21-L44`, `L225-L365`).
2. A paid Request-backed child can create a `RefundRequest` keyed to that `tripId`; admin approval processes that refund (`cancel/route.ts:L393-L445`; `admin/refund-requests/[id]/approve/route.ts:L38-L91`, `L135-L137`).
3. No Request-level passenger cancellation/refund endpoint was found. Thus a child-level refund does not by itself define how the Request aggregate payment/status or sibling Trips should change.

## D. Known-gap analysis

### Claim-before-capture (must fix before enabling multi-day Requests)

In the mixed Request webhook, `Request` is first claimed as `paid/submitted` (`payments/webhook/route.ts:L573-L584`), then wallet reservation capture occurs (`L647-L659`). If `captureReservation` returns `null`, the handler exits (`L656-L659`) before updating the Payment to a final state. The Request can remain paid while its Payment is in-flight and wallet reservation is uncaptured. Webhook event/transaction ID is claimed before this branch (`L345-L369`), so replay can be rejected instead of retrying capture. Request verify has the same ordering in wallet-only and Kashier paths (`payments/kashier.ts:L109-L148`, `L169-L240`); verification may return pending once, then short-circuit as paid (`L92`).

The standalone Trip settlement is materially safer: its conditional claim, wallet capture and ledger changes are inside a Mongo transaction; capture failure aborts it (`standaloneTripSettlement.ts:L64-L96`, `L98-L176`).

**Minimal outline:** do not expose Request `paid/submitted` until payment-provider success and wallet capture both commit. Perform Request + every child Trip + Payment/ledger updates in one supported Mongo transaction (or a recoverable explicit settlement state machine); only mark webhook event processed after durable completion, or make replay safely resume the same idempotent settlement. Add injected capture-failure/replay tests for Request webhook, callback and wallet-only verification.

### Promo usage not released for Request terminal states (must fix before enabling)

`PromoCodeUsage` records are per Trip (`PromoCodeUsage.ts:L5-L7`). Request expiry transitions Request/children without calling `releasePromoCodeUsageForTrip` (`services/requests.ts:L24-L70`; `api/trips/expire/route.ts:L48-L64`). Standalone expiry does release it (`services/standaloneTripExpiry.ts:L25-L50`; helper `promoCode.ts:L204-L245`). Admin rejection of a waiting-list Request also releases per-child usage (`admin/waiting-list/[id]/route.ts:L225-L271`), so behavior differs by terminal path. A current Request-level passenger cancellation endpoint was not found; existing cancellation is per Trip.

**Minimal outline:** centralize Request terminal transition and idempotently release still-reserved usage for every child Trip, with exactly-once promo counter adjustment and conditional status change. Add expiry, cancellation/rejection, retries and concurrent-terminal-transition tests. Preserve consumed/paid usage according to the final promo semantics.

## F. Decisions required

1. Is payment strictly one per multi-day Request and one per standalone one-day Trip? May a Request child ever be checked out or paid independently? Recommended: **no**.
2. Is cancellation of one child allowed? If yes, who owns Request status/payment status, how are sibling Trips affected, and how is a partial refund calculated against a single group charge?
3. Which state is authoritative: Request group status or child Trip statuses? Specify allowed transitions and synchronization rules for waitlist approval, cancellation, expiry and refund.
4. Does a promo apply once per Request or independently to each child Trip? Existing historical creation applied and reserved it per Trip instance; retain or intentionally change that behavior.
5. Is waitlist review one atomic group decision or can an operator approve/reject individual days? Existing legacy UI/API treats Request-backed children as a group.
6. Should passenger history group all Request children in all tabs, or may “all” remain individual Trip rows? Should date filters return only selected children or every sibling of a matching Request?
7. Confirm seven *selected dates* (within current booking window) and existing maximum of 10 cycles; decide whether silently cap dates to seven or reject overflow. Historical route silently truncated dates.
8. Who configures the recurring expiry call and what is the guaranteed schedule/secret rotation?
9. Should schema/index naming be corrected from `Payment.bookingId -> Booking` to an explicit polymorphic/group identity, or is the current resolver contract intentionally retained?
